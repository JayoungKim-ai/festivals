# 전국 축제 정보 검색 서비스 — 개발 계획

PRD(`docs/PRD.md`)를 기준으로 하며, **이미 구성된 보일러플레이트 위에서 기능 구현만** 진행한다.

---

## 1. 전제 및 제외 범위

### 1.1 이미 준비된 것 (재작업하지 않음)

| 영역 | 현재 상태 |
| ---- | --------- |
| 프로젝트 구조 | `frontend/` (React + Vite), `backend/` (FastAPI), `docs/` |
| 백엔드 | FastAPI, CORS, SQLite(`app.db`) 연결, SQLModel, `/health` |
| 프론트엔드 | Vite React, `api.js`의 `BASE_URL`·`checkHealth`, 연결 확인 화면 |
| 의존성 | `backend/requirements.txt`에 fastapi, uvicorn, sqlmodel, requests, python-dotenv |
| 실행 환경 | conda 환경 `festival` |

### 1.2 계획에서 제외하는 단계

- 프로젝트 생성·scaffold
- 가상환경 생성·기본 패키지 설치 안내
- FastAPI/React 초기 세팅, CORS·DB 엔진 재구성
- 로그인·리뷰·결제·관리자 화면 등 PRD 제외 범위(§7)

### 1.3 개발 원칙

1. **한 번에 하나의 기능**만 구현한다.
2. 작업은 `docs/TASKS.md` 체크리스트를 따른다.
3. 프론트엔드는 **공공데이터 API를 직접 호출하지 않는다**. FastAPI 내부 API만 사용한다.
4. API 키는 `.env`에만 두고 코드에 하드코딩하지 않는다.
5. MVP를 완성한 뒤에만 지역 필터·지도·즐겨찾기를 진행한다.

## 2. 전체 개발 순서 개요

```
[Phase 0] 확인만
    └─ 기존 보일러플레이트·실행 방식 파악 (코드 추가 없음)

[Phase 1] 백엔드 MVP
    ├─ 1-1. Festival 모델·DB 스키마
    ├─ 1-2. 환경변수·공공데이터 API 클라이언트
    ├─ 1-3. 응답 정제·동기화(sync) 로직
    └─ 1-4. 조회 API (목록·검색·상세)

[Phase 2] 프론트엔드 MVP
    ├─ 2-1. 라우팅·공통 레이아웃
    ├─ 2-2. API 클라이언트 확장
    ├─ 2-3. 축제 찾기(목록·검색)
    ├─ 2-4. 축제 상세
    └─ 2-5. 서비스 소개·상태 UI·반응형

[Phase 3] MVP 검증
    └─ PRD §9.1·§9.2 완료 기준 점검

[Phase 4] 추가 기능 (MVP 이후)
    ├─ 4-1. 지역 필터
    ├─ 4-2. 지도 표시
    └─ 4-3. 즐겨찾기
```

권장 흐름은 항상 **백엔드가 데이터를 준비 → 프론트가 내부 API로 소비**이다.

---

## 3. Phase 0 — 현황 확인 (구현 없음)

- `backend/main.py`: 엔진·lifespan·CORS·health만 존재. 도메인 모델·비즈니스 API 없음.
- `frontend/src`: 연결 확인용 `App.jsx` / `api.js`만 존재.
- 실행: conda `festival` + `uvicorn main:app --reload`, `npm run dev`.

이 단계에서는 문서를 읽고 실행 가능한지만 확인한다.

---

## 4. Phase 1 — 백엔드 MVP

목표: 공공데이터 → 정제 → SQLite 저장 → 내부 조회 API 제공.

### 4-1. Festival 모델 및 DB 스키마

PRD §6.5 필드를 기준으로 SQLModel 모델을 정의한다.

- `id`, `external_id`, `festival_name`, `location`, `start_date`, `end_date`
- `description`, `managing_org`, `hosting_org`, `sponsoring_org`
- `phone`, `homepage_url`, `related_info`, `road_address`, `parcel_address`
- `latitude`, `longitude` (MVP에서 UI 미사용이어도 저장 가능하면 확보)
- `created_at`, `updated_at`
- `external_id`(또는 대체 키)에 대한 유니크·중복 방지
- 축제명 검색을 위한 인덱스 검토

결과물: 서버 기동 시 `festivals` 테이블 생성.

### 4-2. 환경변수 및 공공데이터 API 클라이언트

- `.env`에 공공데이터 API 인증키·엔드포인트 등 설정
- `.env.example`로 필요한 키 이름만 문서화 (실제 키는 커밋하지 않음)
- `python-dotenv`로 서버에서만 키 로드
- `requests`로 외부 API 호출 (응답 형식 XML/JSON, 페이지네이션, 요청 제한 확인)

### 4-3. 데이터 정제 및 동기화

- 외부 필드 → 내부 컬럼 매핑
- 날짜·빈 값·null 정규화
- `POST /api/festivals/sync` 또는 동등한 개발용 동기화 경로
  - 일반 사용자 UI에는 노출하지 않음
  - `external_id` 기준 upsert (없으면 축제명+시작일+장소 등 임시 키)
  - 일부 건 실패 시에도 전체 중단 없이 로그 기록

결과물: SQLite에 정제된 축제 데이터가 쌓임.

### 4-4. 축제 조회 API

| 메서드 | 경로 | 설명 |
| ------ | ---- | ---- |
| `GET` | `/api/festivals` | 목록. `search`, `page`, `size` |
| `GET` | `/api/festivals/{festival_id}` | 상세 |
| `POST` | `/api/festivals/sync` | 데이터 수집·갱신 (개발/수동용) |

- 검색: 축제명 부분 일치, 대소문자 무시, 앞뒤 공백 제거
- 파라미터 바인딩/ORM으로 SQL 인젝션 방지
- 외부 API 원본을 그대로 프론트에 넘기지 않음

## 5. Phase 2 — 프론트엔드 MVP

목표: 내부 API만으로 찾기·검색·상세·소개 화면을 제공한다.

### 5-1. 라우팅 및 공통 레이아웃

- React Router로 화면 분기
  - `/` 또는 `/festivals` — 축제 찾기
  - `/festivals/:id` — 상세
  - `/about` — 서비스 소개
- 공통 헤더(서비스명, 축제 찾기, 서비스 소개), 푸터(데이터 출처·안내)

### 5-2. API 클라이언트 확장

- 기존 `frontend/src/api.js`에 목록·상세 호출 함수 추가
- `BASE_URL`은 FastAPI만 가리킴 (공공데이터 URL 금지)
- 네트워크·HTTP 오류를 UI에서 구분 가능하도록 처리

### 5-3. 축제 찾기 화면

- 진입 시 전체 목록 조회
- 검색창 + 검색 버튼 + Enter 검색
- 빈 검색어 → 전체 목록
- 목록 카드: 축제명, 개최기간, 개최장소, 주소 일부, 상세 이동
- 결과 건수, 로딩 / 결과 없음 / 오류 상태

### 5-4. 축제 상세 화면

- 목록에서 선택 시 상세 이동, “목록으로 돌아가기”
- PRD §4.3 표시 항목
- 값 없음 → “정보 없음”
- 홈페이지는 외부 링크, 날짜는 `YYYY.MM.DD ~ YYYY.MM.DD` 형식
- 전화번호 링크는 가능하면 `tel:` 검토

### 5-5. 서비스 소개·상태 UI·반응형

- 소개·주요 기능·이용 방법·데이터 출처·갱신·유의사항
- 데스크톱·모바일 기본 반응형
- 보일러플레이트 연결 확인 UI는 서비스 UI로 교체 (필요 시 health는 개발용으로만 유지)

---

## 6. Phase 3 — MVP 검증

PRD §9.1·§9.2를 기준으로 수동 확인한다.

핵심 사용자 시나리오:

1. 축제 찾기 접속
2. 축제명 검색
3. 결과 목록 확인
4. 축제 선택
5. 기간·장소·내용·연락처·홈페이지·주소 확인

체크포인트:

- 동기화 후 DB에 데이터 존재, 재동기화 시 불필요 중복 없음
- 프론트에 API 키·공공데이터 직접 호출 없음
- 로딩·빈 결과·오류 문구 표시

MVP 완료 후에만 Phase 4로 진행한다.

## 7. Phase 4 — 추가 기능 (MVP 이후)

순서: **지역 필터 → 지도 → 즐겨찾기**.

### 7-1. 지역 필터

**백엔드**

- 시도/시군구 필드 존재 여부 확인. 없으면 주소에서 지역 추출 전략 결정
- `GET /api/festivals`에 지역 쿼리 파라미터 추가
- 검색어 + 지역 동시 적용

**프론트엔드**

- 축제 찾기 화면에 지역 선택 UI
- 전체/특정 지역, 검색과 함께 적용

### 7-2. 지도 표시

**사전 확인**

- DB의 `latitude`/`longitude` 확보 여부
- 없으면 지오코딩 시점(동기화 시 vs 조회 시) 결정
- 좌표 없는 축제는 지도 비표시

**구현**

- Leaflet + 타일 서비스 선정(약관·호출 제한 확인)
- 상세 화면에 지도 섹션 추가

### 7-3. 즐겨찾기

**저장**

- 로그인 없음, `localStorage`에 축제 `id`만 저장
- 표시 시 서버에서 최신 정보 재조회

**화면**

- 목록·상세에 추가/삭제 토글
- `/favorites` 즐겨찾기 목록, 헤더 메뉴
- 빈 목록·삭제된/조회 불가 ID는 오류 없이 정리·안내

## 8. 권장 작업 단위와 의존 관계

```
Festival 모델
    → 공공데이터 클라이언트
        → sync·정제·저장
            → 목록/검색/상세 API
                → 프론트 API 모듈
                    → 레이아웃·라우팅
                        → 찾기 화면
                            → 상세 화면
                                → 소개·반응형·MVP 검증
                                    → 지역 필터 → 지도 → 즐겨찾기
```

앞 단계가 동작하지 않으면 다음 단계로 넘어가지 않는다.

---

## 9. 완료 정의 요약

| 단계 | 완료 정의 |
| ---- | --------- |
| 백엔드 MVP | sync로 DB 적재, 목록·검색·상세 API 정상, 키는 서버 `.env`만 |
| 프론트 MVP | 찾기·검색·상세·소개 동작, 상태 UI·반응형, 내부 API만 호출 |
| MVP 전체 | PRD §9.1·§9.2 충족 |
| 추가 기능 | PRD §9.3 충족 (지역·지도·즐겨찾기) |

세부 체크 항목은 `docs/TASKS.md`를 따른다.
