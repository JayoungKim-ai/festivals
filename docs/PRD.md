# 전국 축제 정보 검색 서비스 PRD

## 1. 제품 개요

### 1.1 제품명

전국 축제 정보 검색 서비스
※ 제품명은 임시 명칭이며 추후 별도 브랜딩 가능

### 1.2 제품 설명

전국에서 개최되는 축제 정보를 한곳에서 검색하고, 축제의 일정·장소·연락처·홈페이지·주소 등 상세 정보를 확인할 수 있는 웹서비스다.

공공데이터 API에서 축제 데이터를 수집한 뒤 FastAPI 서버를 통해 SQLite 데이터베이스에 저장하고, React 기반 프론트엔드에서 해당 데이터를 조회한다.

MVP에서는 축제명 검색, 축제 목록 조회, 축제 상세 정보 확인 기능을 제공한다. 이후 지역 필터, 지도 표시, 즐겨찾기 기능을 단계적으로 추가한다.

### 1.3 제품 목적

사용자가 주말이나 연휴에 방문할 축제를 빠르게 찾고, 필요한 정보를 여러 사이트에서 별도로 검색하지 않아도 한 화면에서 확인할 수 있도록 한다.

### 1.4 핵심 가치

* 전국 축제 정보를 한곳에서 확인할 수 있다.
* 축제명으로 원하는 축제를 빠르게 검색할 수 있다.
* 축제 일정, 장소, 연락처, 주소, 홈페이지를 한 번에 확인할 수 있다.
* 추가 개발 이후에는 관심 있는 축제를 저장하고 다시 확인할 수 있다.

### 1.5 데이터 처리 구조

서비스의 기본 데이터 흐름은 다음과 같다.

1. FastAPI 서버가 공공데이터 API를 호출한다.
2. 외부 API 응답 데이터를 서비스 내부 데이터 구조에 맞게 정제한다.
3. 정제된 축제 데이터를 SQLite 데이터베이스에 저장한다.
4. React 프론트엔드는 FastAPI 서버가 제공하는 내부 API를 호출한다.
5. FastAPI 서버는 SQLite에 저장된 데이터를 조회해 프론트엔드에 반환한다.

프론트엔드에서는 공공데이터 API를 직접 호출하지 않는다.

## 2. 대상 사용자

### 2.1 주요 사용자

주말이나 연휴에 방문할 만한 축제를 찾는 일반 사용자

### 2.2 사용자 특성

* 특정 지역에서 열리는 축제를 찾고 싶어 한다.
* 축제 일정과 개최 장소를 빠르게 확인하고 싶어 한다.

### 2.3 주요 이용 상황

* 여행 지역 주변의 축제를 확인하는 경우

* 관심 있는 축제를 저장해 나중에 다시 확인하는 경우

## 3. 문제 정의

### 3.1 정보 분산

축제 정보가 공공기관, 지방자치단체, 관광 관련 사이트 등 여러 곳에 분산되어 있어 사용자가 직접 여러 사이트를 확인해야 한다.

### 3.2 정보 확인의 불편

축제 기간, 개최 장소, 문의 전화번호, 홈페이지, 상세 주소와 같은 정보가 서로 다른 화면이나 사이트에 제공되어 한 번에 확인하기 어렵다.

### 3.3 검색의 비효율

사용자가 특정 축제명을 알고 있더라도 해당 축제의 공식 정보나 최신 정보를 찾기 위해 여러 검색 결과를 확인해야 할 수 있다.

### 3.4 관심 축제 관리의 어려움

관심 있는 축제를 발견해도 별도로 저장하거나 다시 찾아볼 수 있는 기능이 부족하다.

### 3.5 해결 방향

서비스는 공공데이터 API를 통해 축제 정보를 수집하고 표준화하여 제공한다. 사용자는 하나의 웹서비스에서 축제를 검색하고, 목록과 상세 정보를 확인할 수 있다.

추가 개발 단계에서는 지역 필터, 지도 표시, 즐겨찾기 기능을 제공해 탐색성과 재방문 편의성을 높인다.

## 4. 주요 기능

### 4.1 축제 목록 조회

#### 기능 설명

데이터베이스에 저장된 축제 정보를 목록 형태로 제공한다.

#### 표시 항목

목록 카드에는 다음 정보를 우선 표시한다.

* 축제명
* 개최장소
* 시작일자
* 종료일자
* 소재지 주소 일부
* 상세 보기 버튼 또는 상세 페이지 이동 링크

#### 동작

* 사용자가 축제 찾기 화면에 진입하면 축제 목록을 조회한다.
* 목록의 특정 축제를 선택하면 축제 상세 화면으로 이동한다.
* 데이터가 없을 경우 빈 상태 안내 문구를 표시한다.
* 서버 오류가 발생하면 오류 안내 문구를 표시한다.

---

### 4.2 축제 이름 검색

#### 기능 설명

사용자가 입력한 검색어를 기준으로 축제명에 해당 검색어가 포함된 축제를 조회한다.

#### 검색 기준

* 검색 대상 필드: 축제명
* 검색 방식: 부분 일치
* 대소문자 구분 없음
* 검색어 앞뒤 공백 제거

#### 동작

* 검색어를 입력하고 검색 버튼을 누르면 검색 결과를 표시한다.
* Enter 키 입력으로도 검색할 수 있다.
* 검색어가 비어 있으면 전체 목록을 표시한다.
* 검색 결과가 없으면 “검색 결과가 없습니다” 메시지를 표시한다.

---

### 4.3 축제 상세 보기

#### 기능 설명

사용자가 선택한 축제의 전체 정보를 상세 화면에서 확인할 수 있도록 한다.

#### 표시 항목

* 축제명
* 개최장소
* 시작일자
* 종료일자
* 축제내용
* 주관기관명
* 주최기관명
* 후원기관명
* 전화번호
* 홈페이지주소
* 관련정보
* 소재지도로명주소
* 소재지지번주소

#### 표시 규칙

* 값이 없는 항목은 빈 문자열로 표시하지 않고 “정보 없음”으로 표시한다.
* 홈페이지주소가 존재하면 클릭 가능한 외부 링크로 제공한다.
* 전화번호가 존재하면 모바일 환경에서 전화 연결이 가능하도록 링크 처리를 검토한다.
* 축제내용은 줄바꿈과 긴 문장을 고려해 읽기 쉬운 형태로 표시한다.
* 날짜는 일관된 형식으로 표시한다.

예시:

`2026.05.01 ~ 2026.05.05`

### 4.4 지역 필터

#### 개발 단계

MVP 완성 후 추가 개발

#### 기능 설명

사용자가 지역을 선택하여 해당 지역의 축제만 확인할 수 있도록 한다.

#### 예상 동작

* 전체 지역 또는 특정 지역을 선택할 수 있다.
* 검색어와 지역 필터를 동시에 적용할 수 있다.
* 지역 정보는 도로명주소, 지번주소 또는 공공데이터의 지역 관련 필드를 기준으로 구성한다.

#### 추가 확인 사항

공공데이터에 별도의 시도명·시군구명 필드가 있는지 확인한다. 별도 필드가 없다면 주소 문자열에서 지역명을 추출하는 방식이 필요하다.

### 4.5 지도 표시

#### 개발 단계

MVP 완성 후 추가 개발

#### 기능 설명

축제 상세 화면에서 축제 개최 위치를 지도에 표시한다.

#### 기술

* Leaflet 사용
* 지도 타일 제공 서비스는 별도 선정
* 위도와 경도 데이터가 필요함

#### 추가 확인 사항

공공데이터에 위도·경도 값이 포함되어 있는지 확인해야 한다.

위도·경도가 제공되지 않는 경우 다음 중 하나가 필요하다.

* 주소를 좌표로 변환하는 지오코딩 API 사용
* 데이터 수집 시 주소를 좌표로 변환해 DB에 저장
* 좌표를 확보할 수 없는 축제는 지도 표시 제외

---

### 4.6 즐겨찾기 추가·삭제

#### 개발 단계

MVP 완성 후 추가 개발

#### 기능 설명

사용자가 관심 있는 축제를 브라우저에 저장하고 다시 확인할 수 있도록 한다.

#### 저장 방식

* 로그인 없이 `localStorage` 사용
* 즐겨찾기에는 축제의 고유 식별자를 저장
* 화면 표시 시 저장된 식별자를 기준으로 서버에서 축제 정보를 조회

#### 동작

* 축제 목록 또는 상세 화면에서 즐겨찾기를 추가할 수 있다.
* 이미 저장된 축제는 활성화된 즐겨찾기 상태로 표시한다.
* 즐겨찾기 버튼을 다시 누르면 삭제한다.
* 즐겨찾기 목록에서 저장된 축제를 다시 열 수 있다.

#### 제약사항

* 동일 브라우저와 동일 기기에서만 유지된다.
* 브라우저 데이터 삭제 시 즐겨찾기도 삭제될 수 있다.
* 다른 기기나 브라우저 간 동기화는 지원하지 않는다.

## 6. MVP 범위

### 6.1 MVP 목표

사용자가 축제명을 검색하고, 검색 결과 목록에서 축제를 선택해 상세 정보를 확인할 수 있는 상태를 MVP 완료로 정의한다.

### 6.2 MVP 포함 기능

* 축제 찾기 화면
* 전체 축제 목록 조회
* 축제 이름 검색
* 축제 목록 표시
* 축제 상세 화면
* 서비스 소개 화면
* 공공데이터 API 호출
* 공공데이터 응답 정제
* SQLite 데이터 저장
* FastAPI 기반 축제 조회 API
* React와 FastAPI 연동
* 로딩, 빈 결과, 오류 상태 처리

### 6.3 MVP 데이터 요구사항

* 공공데이터 API에서 축제 정보를 정상적으로 가져올 수 있어야 한다.
* 외부 데이터의 각 필드를 내부 DB 컬럼과 연결해야 한다.
* 축제를 구분할 수 있는 고유 식별자가 필요하다.
* 동일 축제가 중복 저장되지 않도록 기준을 정의해야 한다.
* 데이터가 갱신될 때 기존 데이터의 추가·수정 여부를 처리해야 한다.

### 6.4 MVP 권장 API 구조

#### 축제 목록 조회

`GET /api/festivals`

주요 쿼리 파라미터:

* `search`: 축제명 검색어
* `page`: 페이지 번호
* `size`: 페이지당 데이터 수

#### 축제 상세 조회

`GET /api/festivals/{festival_id}`

#### 데이터 수집 또는 갱신

`POST /api/festivals/sync`

데이터 동기화 API는 일반 사용자 화면에 직접 노출하지 않는다. 관리자 화면은 개발하지 않으므로 개발 환경에서 수동 실행하거나 별도의 실행 스크립트로 구성할 수 있다.

### 6.5 MVP 권장 DB 필드

| 필드명            | 설명            |
| -------------- | ------------- |
| id             | 서비스 내부 고유 식별자 |
| external_id    | 공공데이터 원본 식별자  |
| festival_name  | 축제명           |
| location       | 개최장소          |
| start_date     | 시작일자          |
| end_date       | 종료일자          |
| description    | 축제내용          |
| managing_org   | 주관기관명         |
| hosting_org    | 주최기관명         |
| sponsoring_org | 후원기관명         |
| phone          | 전화번호          |
| homepage_url   | 홈페이지주소        |
| related_info   | 관련정보          |
| road_address   | 소재지도로명주소      |
| parcel_address | 소재지지번주소       |
| latitude       | 위도            |
| longitude      | 경도            |
| created_at     | 최초 저장일시       |
| updated_at     | 최종 수정일시       |

위도와 경도는 MVP에서 사용하지 않더라도 향후 지도 기능을 고려해 데이터가 제공된다면 저장할 수 있다.

### 6.6 데이터 동기화 기준

* 공공데이터 API 응답을 그대로 프론트엔드에 전달하지 않는다.
* 필드명과 데이터 형식을 내부 기준으로 변환한다.
* 날짜는 DB 저장 전에 일관된 날짜 형식으로 변환한다.
* 빈 문자열, `null`, 누락 필드의 처리 기준을 정의한다.
* `external_id`가 존재하면 해당 값을 중복 판단 기준으로 사용한다.
* 원본 식별자가 없다면 축제명, 시작일자, 개최장소 등의 조합을 임시 중복 기준으로 사용할 수 있다.
* 동기화 중 일부 데이터에 오류가 발생하더라도 전체 작업이 중단되지 않도록 오류 로그를 남긴다.

### 6.7 MVP 비기능 요구사항

* 데스크톱과 모바일 브라우저에서 사용할 수 있어야 한다.
* 기본적인 반응형 화면을 제공해야 한다.
* 검색 결과는 사용자가 불편을 느끼지 않는 수준으로 응답해야 한다.
* 서버 오류와 네트워크 오류를 사용자에게 이해 가능한 문장으로 표시해야 한다.
* API 키와 인증 정보는 프론트엔드 코드에 포함하지 않는다.
* 공공데이터 API 인증키는 서버 환경변수로 관리한다.

## 8. 기술 고려사항

### 8.1 프론트엔드

* React
* React Router를 이용한 화면 이동
* FastAPI 내부 API 호출
* 반응형 UI 적용
* 검색어 및 화면 상태 관리
* 추가 개발 시 `localStorage`를 이용한 즐겨찾기 관리

### 8.2 백엔드

* FastAPI
* 공공데이터 API 호출
* 외부 응답 데이터 검증 및 변환
* SQLite 데이터 저장 및 조회
* 축제 목록·검색·상세 API 제공
* CORS 설정
* 환경변수 기반 API 인증키 관리
* 데이터 동기화 로직 제공

### 8.3 데이터베이스

* SQLite
* 축제 기본 정보 저장
* 외부 데이터 식별자와 내부 식별자 관리
* 중복 데이터 방지
* 검색 성능을 고려한 축제명 인덱스 검토
* 추후 DB 변경 가능성을 고려한 데이터 접근 계층 구성 권장

### 8.4 외부 API 연동

* 공공데이터 API의 요청 제한 확인
* 인증키 노출 방지
* 응답 형식이 XML인지 JSON인지 확인
* 페이지네이션 방식 확인
* 전체 데이터 수집을 위한 반복 호출 처리
* API 호출 실패 시 재시도 또는 오류 기록
* 필드 누락과 데이터 타입 불일치 처리
* 데이터 갱신 주기 결정

### 8.5 지도

* Leaflet 사용
* 지도 기능은 MVP 이후 개발
* 지도 타일 서비스의 이용약관과 호출 제한 확인
* 위도·경도 제공 여부 확인
* 주소 기반 지오코딩이 필요한 경우 별도 API 검토

### 8.6 즐겨찾기

* 로그인 없이 `localStorage` 사용
* 즐겨찾기에는 축제 전체 데이터를 저장하기보다 고유 ID를 저장하는 방식을 권장
* 서버 데이터가 변경되었을 때 최신 정보를 다시 조회할 수 있도록 구성
* 브라우저 저장소 삭제 시 데이터가 사라질 수 있음을 안내

### 8.7 보안

* 공공데이터 API 인증키를 프론트엔드에 노출하지 않는다.
* 인증키와 서버 설정값은 `.env` 파일로 관리한다.
* `.env` 파일은 Git 저장소에 포함하지 않는다.
* 외부 URL은 허용된 프로토콜인지 확인한다.
* 사용자 검색어를 그대로 SQL문에 결합하지 않는다.
* ORM 또는 파라미터 바인딩을 사용한다.

### 8.8 데이터 품질

공공데이터에는 다음 문제가 존재할 수 있으므로 예외 처리가 필요하다.

* 날짜 형식 불일치
* 주소 누락
* 전화번호 형식 불일치
* 홈페이지주소 오류
* 동일 축제 중복
* 종료된 축제 정보 잔존
* 축제명 표기 차이
* 기관명 누락
* 위도·경도 누락

서비스에서는 원본 데이터에 없는 정보를 임의로 생성하지 않으며, 값이 없는 항목은 “정보 없음”으로 표시한다.

## 9. 완료 기준

### 9.1 MVP 기능 완료 기준

다음 조건을 모두 충족하면 MVP가 완료된 것으로 판단한다.

1. FastAPI 서버가 공공데이터 API를 정상적으로 호출할 수 있다.
2. 외부 API에서 가져온 축제 데이터가 SQLite에 저장된다.
3. 동일한 데이터를 다시 수집해도 불필요한 중복 데이터가 생성되지 않는다.
4. React 화면에서 전체 축제 목록을 조회할 수 있다.
5. 사용자가 축제명을 입력해 검색할 수 있다.
6. 검색 결과가 축제 목록으로 표시된다.
7. 사용자가 목록에서 축제를 선택할 수 있다.
8. 선택한 축제의 상세 화면이 표시된다.
9. 상세 화면에 요구된 축제 정보가 표시된다.
10. 데이터가 없는 필드는 오류 없이 “정보 없음”으로 처리된다.
11. 서비스 소개 화면을 확인할 수 있다.
12. 프론트엔드가 공공데이터 API를 직접 호출하지 않는다.
13. API 인증키가 프론트엔드 코드에 노출되지 않는다.
14. 모바일과 데스크톱 환경에서 주요 기능을 사용할 수 있다.
15. 로딩, 검색 결과 없음, 서버 오류 상태가 화면에 표시된다.

### 9.2 MVP 사용자 시나리오 완료 기준

사용자가 다음 흐름을 중단 없이 수행할 수 있어야 한다.

1. 축제 찾기 화면에 접속한다.
2. 축제명을 검색한다.
3. 검색 결과 목록을 확인한다.
4. 목록에서 원하는 축제를 선택한다.
5. 축제의 개최기간, 장소, 내용, 연락처, 홈페이지, 주소를 확인한다.

위 흐름이 정상적으로 동작하면 MVP의 핵심 성공 기준을 충족한 것으로 본다.

### 9.3 추가 개발 완료 기준

다음 조건을 충족하면 추가 개발 범위가 완료된 것으로 판단한다.

1. 사용자가 지역별로 축제를 필터링할 수 있다.
2. 검색어와 지역 필터를 함께 적용할 수 있다.
3. 축제 상세 화면에서 위치를 지도로 확인할 수 있다.
4. 사용자가 축제를 즐겨찾기에 추가할 수 있다.
5. 즐겨찾기를 삭제할 수 있다.
6. 브라우저를 닫았다가 다시 열어도 즐겨찾기가 유지된다.
7. 즐겨찾기 목록에서 저장한 축제를 다시 열 수 있다.
8. 삭제되거나 조회할 수 없는 축제가 즐겨찾기에 남아 있을 경우 오류 없이 처리된다.

### 9.4 최종 성공 기준

* MVP 성공: 사용자가 축제를 검색하고 목록에서 선택하여 상세 정보를 확인할 수 있다.
* 추가 개발 성공: 사용자가 관심 있는 축제를 즐겨찾기에 저장하고 이후 다시 열어볼 수 있다.
